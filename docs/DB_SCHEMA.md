# Database Schema

> **Source of truth:** `sql/init/*.sql`. This document was generated by parsing `sql/init/01_ddl.sql`, `02_views.sql`, `03_functions.sql`, `04_procedures.sql` and `05_triggers.sql`, so table, column and constraint listings match the SQL files exactly.
> **Execution status:** these scripts have **not been executed against a live PostgreSQL instance** in this project's validation so far (no database was available in the review environment). They are syntactically balanced but must be run (`docker compose up -d`) to be considered verified. See [TESTING.md](./TESTING.md).
> **Prototype relationship:** the React prototype does not read this database. See [Schema gaps](#schema-gaps-and-prototype-mismatches).

Target: PostgreSQL 16 (`postgres:16-alpine` in `docker-compose.yml`). Extension required: `pgcrypto`.

## Triggers

| Trigger | Timing | Event | Table |
|---|---|---|---|
| `trg_applications_validate_insert` | BEFORE | INSERT | `applications` |
| `trg_applications_validate_status` | BEFORE | UPDATE | `applications` |
| `trg_applications_create_offer` | AFTER | UPDATE | `applications` |
| `trg_applications_log_status` | AFTER | INSERT OR UPDATE | `applications` |
| `trg_interviews_validate_insert` | BEFORE | INSERT | `interviews` |
| `trg_students_lowercase_email` | BEFORE | INSERT OR UPDATE OF email | `students` |
| `trg_users_lowercase_email` | BEFORE | INSERT OR UPDATE OF email | `users` |
| `trg_applications_notify` | AFTER | UPDATE | `applications` |
| `trg_interviews_notify` | AFTER | INSERT | `interviews` |

Key trigger rules (see `05_triggers.sql` for the exact code):

- `trg_applications_validate_insert`: job must be OPEN, deadline not passed, student academically eligible (`fn_is_eligible`) and allowed by the tier policy (`fn_policy_allows`); new applications always start as `APPLIED`.
- `trg_applications_validate_status`: allowed transitions are APPLIED -> SHORTLISTED / REJECTED / WITHDRAWN, SHORTLISTED -> INTERVIEW / REJECTED / WITHDRAWN, INTERVIEW -> SELECTED / REJECTED / WITHDRAWN. SELECTED, REJECTED and WITHDRAWN are final.
- `trg_applications_create_offer`: on SELECTED creates a PENDING offer unless the student already holds a placement of the same or higher tier.
- `sp_respond_to_offer` (procedure): accepting creates or upgrades the `placements` row, marks the replaced offer SUPERSEDED and LOCKs same/lower-tier pending offers.

## Seed data (`06_seed.sql`)

Written (not executed) to produce: 4 departments, 12 skills, 12 students, 5 companies with contacts, 7 jobs (one CLOSED), 3 user accounts (ADMIN, STAFF, one STUDENT), 14 applications moved through the lifecycle with interview rounds, 5 accepted offers and 5 placements, plus trigger-generated notifications and status history. Passwords are hashed with `pgcrypto` and are development-only demo values.

## Schema gaps and prototype mismatches

The React prototype (`prototype/`) models more and differently than this schema. These are the verified differences (details: [KNOWN_ISSUES.md](./KNOWN_ISSUES.md), [INTEGRATION_PLAN.md](./INTEGRATION_PLAN.md)).

| Topic | Prototype (`prototype/src/services/mockApi.js`) | SQL schema | Consequence |
|---|---|---|---|
| Application status | APPLIED, UNDER_REVIEW, SHORTLISTED, ASSESSMENT, INTERVIEW, SELECTED, OFFER_RELEASED, OFFER_ACCEPTED, OFFER_DECLINED, OFFER_EXPIRED, REJECTED | APPLIED, SHORTLISTED, INTERVIEW, SELECTED, REJECTED, WITHDRAWN | UNDER_REVIEW and ASSESSMENT have no DB value; OFFER_* is derived from `offers`; WITHDRAWN does not exist in the prototype |
| Offer status | PENDING, ACCEPTED, DECLINED, EXPIRED | PENDING, ACCEPTED, DECLINED, LOCKED, SUPERSEDED | EXPIRED missing in DB; LOCKED / SUPERSEDED not shown in the prototype |
| Value casing | `Super Dream`, `Full-time`, `Beginner`, `PASSED` | `SUPER_DREAM`, `FULL_TIME`, `BEGINNER`, `CLEARED` | API layer must map values |
| Interview result | PENDING, PASSED (and others in code) | PENDING, CLEARED, REJECTED | Rename or map |
| Assessment round | Separate application stage ASSESSMENT | `ONLINE_TEST` is an interview `round_type` | Model decision needed |
| Notifications | Per recipient (STUDENT, STAFF, ADMIN) with per-user `read_by`, links, dedupe keys | `notifications.student_id` only, single `is_read` | No table for staff/admin notifications or per-user read state |
| Messaging | Conversations, participants, messages | No tables | Entire messaging domain is missing |
| Policies | Policy object (single offer, upgrade multiplier, tier cut-offs, limits) | Rules hard-coded in functions and triggers | No `policies` table; most prototype policy fields are not enforced by either side |
| Staff profile | Title, assigned departments, account status | `users` has only email, role, active flag | No staff profile table |
| Student settings | `studentSettings` object | No table | Missing |
| Job extras | `recruitment_process`, `openings`, `applied_count` | Not present | Missing columns |
| Application detail | Rounds array, status history with explanations | `application_status_history` has status only | Partial |
| Interview detail | Attendance, feedback, timezone, mode | `interviews` has no attendance, feedback, mode | Missing columns |
| Offer detail | `joining_date`, `verified` | Not present | Missing columns |
| Departments | `Computer Science`, `Electronics & Comm.`, ... | `Computer Engineering`, `ENTC`, ... (seed) | Align names |
| Eligibility score | Client formula: 68% skills + 32% CGPA margin, clamped 18..99, penalties | `fn_match_score`: 60% skills + 40% CGPA margin, no clamp | Different numbers for the same student and job |
| OTP | Fixed demo code in the client | `email_otps` with hashed codes | Not connected |

Backend ORM models do not exist yet (`backend/app/models/` is an empty package), so no SQL-versus-ORM mismatch can be reported today.
